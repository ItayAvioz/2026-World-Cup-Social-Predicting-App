# מערכת המולטי-אייג'נט: מה קורה שם, ומה השתנה

זה המסמך שמסביר את הלב של מה שדיברנו עליו במפגש — ה-crew. מה זה, איך זה שונה ממה שהיה, מה
כבר קיים (ובנית בעצמך), ומה עוד חסר.

---

## 1. מ-ensemble ל-crew — ההבדל בשורה אחת

* **מה שיש לך היום- ensemble:** אותו *תפקיד* רץ כמה פעמים. 5 פרומפטים כמעט-זהים שכולם
  מנסים לכתוב את אותו סיכום, ו-Judge בוחר את הטוב מביניהם. זה כמו לשאול 5 כותבים את אותה שאלה
  ולבחור את התשובה הכי טובה.
* **מה שבנינו כאן- crew:** *תפקידים שונים* בשרשרת. אחד מחשב סטטיסטיקות, אחד מתייג אישיות,
  אחד כותב בעברית, אחד שופט. זה כמו צוות מערכת: כתב, עורך, מבקר — כל אחד עבודה אחת.

> הנקודה החשובה מהמפגש: ה-5 שלך הם **אותו תפקיד ×5**, לא 5 אישיויות. ה-Judge הוא התפקיד השני
> האמיתי היחיד שכבר היה לך. ה-crew מוסיף תפקידים *חדשים* — לא עוד עותקים.

## 2. הצינור (pipeline) — מה קורה צעד-צעד

```
   fetch (live, read-only מ-Supabase)
        │  group + members + predictions + games + leaderboard
        ▼
   ┌─────────────┐
   │   Stats     │  פייתון טהור, בלי LLM. מחשב עובדות:
   │             │  מי מוביל, מי עשה הכי הרבה נקודות היום, מי "התקרר",
   │             │  כמה ניחשו במדויק, האם תוצאה הפתיעה את הקבוצה.
   └──────┬──────┘  → StatsBlock (typed)
          │
          ▼
   ┌─────────────┐
   │ Personality │  LLM. עובר על כל שחקן ומתייג סגנון:
   │             │  the_optimist / the_coward / the_sniper / the_ghost ...
   │             │  + evidence — עובדה אמיתית מהדאטה שמצדיקה את התיוג.
   └──────┬──────┘  → list[PlayerStyle] (typed, אחד לכל שחקן)
          │
          ▼
   ┌─────────────┐
   │   Writer    │  LLM. מקבל את העובדות + התיוגים, וכותב את ה-roast בעברית.
   │  (שלך!)     │  זה המקום היחיד שאחראי על שפה.
   └──────┬──────┘  → CrewSummary (text_he)
          │
          ▼
   ┌─────────────┐
   │   Judge     │  LLM (מודל יקר). מנקד accuracy/humor/hebrew/structure 0–10.
   │             │  אם נמוך מסף → מחזיר ל-Writer עם feedback, עד N ניסיונות.
   └─────────────┘  → JudgeVerdict
```

כל חץ הוא **handoff מובנה (typed)**: הפלט של שלב אחד הוא הקלט של הבא, כאובייקט עם schema —
לא בלוב טקסט. זה כל היופי: כל שלב מבודד וניתן לכיוונון בנפרד.

## 3. מה כל סוכן עושה

| סוכן | LLM? | קלט | פלט | קובץ |
|---|---|---|---|---|
| **Stats** | לא | raw data | `StatsBlock` | `app/agents/stats.py` |
| **Personality** | כן | `MemberStat` | `PlayerStyle` | `app/agents/personality.py` |
| **Writer** | כן | facts + tags | `CrewSummary` (עברית) | `app/agents/writer.py` |
| **Judge** | כן | facts + roast | `JudgeVerdict` | `app/agents/judge.py` |

**שים לב ש-Stats הוא לא LLM.** זה בכוונה — בדיוק כמו אצלך ב-EF, מחשבים את העובדות
דטרמיניסטית קודם, ורק אז נותנים אותן למודלים. "סוכן" לא חייב להיות מודל שפה.

---

## 4. למה PydanticAI (ולא LangGraph/CrewAI)

בגלל ש PydanticAI ממשיך בדיוק את מה שכבר עשית — בלי DSL חדש ובלי framework כבד. הוא נותן דבר אחד
מרכזי: **structured output**. כשאתה מגדיר ל-agent ש-`output_type=PlayerStyle`, המודל **מחויב**
להחזיר בדיוק את ה-schema הזה. אין `JSON.parse`, אין "בבקשה תחזיר JSON תקין", אין retry ידני —
ה-framework עושה את כל הלולאה הזו בשבילך.

הדוגמה העובדת המלאה: [`app/agents/personality.py`](../app/agents/personality.py). קרא אותה
מלמעלה למטה — זו ה-class הקטן (`PlayerStyle`) שביקשת לראות במפגש, בקוד שרץ.

## 5. התשובה לשאלת הזהב: Writer מול ה-prompt שאתה כותב היום ⭐

שאלת: *"מה ההבדל בין ה-Writer לבין ה-prompt שאני כותב היום?"*

ההבדל הוא **הקלט והאחריות**:

* היום: prompt אחד שמקבל בלוב JSON, צריך "להבין הכול" ולכתוב.
* ה-Writer: מקבל **אובייקטים typed** — `StatsBlock` (עובדות) + `list[PlayerStyle]` (תיוגים)
  שכבר חושבו עבורו. תפקידו **צר**: עברית בלבד.

ובגלל זה — אתה יכול לכוונן את ה-Writer **לבד**, למדוד אותו עם ה-Judge, ואפילו להחליף לו מודל,
**בלי לגעת** בחישוב הסטטיסטיקות או בתיוג. עם prompt ענק אחד אין לך את ההפרדה הזו.

## 6. מה כבר קיים — דברים שאתה כבר בנית (continuity)

ה-crew הזה **לא** מתחיל מאפס. הוא ממשיך אותך:

| מה | מאיפה זה בא |
|---|---|
| **Judge** | בנית אותו ב-EF (gpt-4o, rubric עם משקלים, hard floor). כאן הוא מנקד את ה-Writer. |
| **חישוב stats דטרמיניסטי** | אתה כבר עושה את זה ב-EF — חישוב לפני LLM. |
| **reproducibility** | seed + temperature נמוך, בדיוק האינסטינקט שלך מ-PR#1 (seed=1). |
| **audit** | שמירת reasoning + scores, בדיוק כמו `ai_judge_runs` שלך. |
| **המעגל הסגור** | הרעיון של Judge שמחזיר feedback — גזרת אותו לבד במפגש. |

## 8. ה-loop של Writer ⇄ Judge (ומה זה "מערכת שמשתפרת לבד")

ב-[`app/crew.py`](../app/crew.py) ה-Writer וה-Judge רצים בלולאה:

1. Writer כותב roast.
2. Judge מנקד (0–10). אם מספיק טוב → שולחים.
3. אם לא → ה-Judge מחזיר **feedback** ("העברית פה צולעת", "ההלצה שטוחה"), וה-Writer מנסה שוב
   עם ההערה. עד `MAX_WRITER_ATTEMPTS`.

זה הצעד הראשון של "מערכת שמשתפרת לבד". הצעד הבא (ה-stretch) — לשמור את הגרסאות שניצחו
ל-`prompt_versions` ולתת ל-Writer ללמוד מהיסטוריה. זה בדיוק ה"מעגל הסגור" שדיברנו עליו, שכבה
אחת מעל ה-Judge שכבר בנית.
